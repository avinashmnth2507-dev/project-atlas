# Contributing to Project Atlas

Thank you for considering a contribution. Project Atlas is a learning-oriented
DevOps and Platform Engineering portfolio centered on a small Flask API. It
demonstrates tests, container hardening, CI and image scanning, local
Kubernetes packaging, and application-level metrics and JSON request logs.

The repository is not a production platform. It does not provision AWS
resources, provide a database or authentication, deploy a live monitoring
stack, or establish that a Kubernetes cluster is currently running. Kustomize
and Helm are alternative ways to manage the same workload. Terraform currently
contains only the AWS provider foundation. Please keep changes aligned with
this implemented scope and distinguish configuration from deployed services.

## Propose a change

For bugs or focused improvements, first search the existing GitHub issues. If
one does not cover the concern, open an issue with a concise description,
relevant context, steps to reproduce for a bug, and the behavior you expect.
For a substantial feature, architecture change, or infrastructure proposal,
open an issue before implementation so the scope and tradeoffs can be discussed.
There are no issue templates or required approvals defined by this repository.

## Fork, branch, and pull request

1. Fork the repository on GitHub.
2. Clone your fork and create a focused branch:

   ```bash
   git clone https://github.com/<your-account>/project-atlas.git
   cd project-atlas
   git switch -c feature/short-description
   ```

3. Make a small, focused change. Keep unrelated formatting or cleanup out of
   the pull request.
4. Run the applicable checks below and review `git diff` before submitting.
5. Push your branch to your fork and open a pull request against
   `avinashmnth2507-dev/project-atlas:main`.

In the pull request description, explain the problem and change, list the checks
you ran and their results, and link any related issue. Update documentation
when behavior, commands, security properties, or project status changes. Add
or adjust tests for application behavior changes. Do not present local checks
as proof of a live CI run or deployment.

## Local development and checks

Ordinary contributions need Python 3.14 and do not require AWS resources, a
Kubernetes cluster, Docker, or paid infrastructure. From the repository root,
prepare the application environment:

```bash
cd app
python3.14 -m venv .venv-atlas002
source .venv-atlas002/bin/activate
python -m pip install -r requirements-dev.txt
```

Run the same Python checks configured in CI:

```bash
python -m compileall -q src tests run.py
python -m ruff check --select E4,E7,E9,F src tests run.py
python -m pytest -q
python -m pip check
```

The pytest suite uses Flask's test client. These commands run from `app/` and
do not start a server or create cloud resources. Container or Kubernetes
configuration changes may have additional relevant local render or validation
commands documented in the corresponding project guides; they still do not
require an AWS deployment for an ordinary contribution.

## Tests, documentation, and review

- Keep changes small and directly related to the issue or stated goal.
- Add or update deterministic tests when application behavior changes.
- Keep README and operational documentation consistent with the actual source
  and configuration. Clearly label historical evidence and unverified
  deployment claims.
- Preserve existing security controls and digest pins unless a reviewed change
  specifically requires updating them.
- Include relevant local command output or a concise result summary in the
  pull request. The GitHub Actions workflow runs on pull requests to `main`,
  but a local pass does not guarantee that CI will pass.

## Security and sensitive information

Do not commit passwords, API keys, tokens, private keys, credentials,
environment files containing secrets, sensitive logs, or personal data.
Generated bytecode, test caches, virtual environments, Terraform state and
plans, and provider working directories do not belong in a contribution.
Check the staged and unstaged file lists before submitting; ignore rules are
not a substitute for reviewing the diff.

For a suspected security vulnerability, email
[avinashmnth2507@gmail.com](mailto:avinashmnth2507@gmail.com) privately. Do not
post exploit details, credentials, or sensitive proof-of-concept material in a
public issue or pull request.
